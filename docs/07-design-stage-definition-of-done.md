# MajorPilot MVP 设计阶段完成标准

> 状态：完成清单 v0.3  
> 更新日期：2026-09-20  
> 适用范围：判断何时可以从详细设计进入脚手架与功能实施

## 1. 设计阶段的完成含义

设计阶段完成不等于网站开发完成，也不等于 RuoYi 已经能够运行。它表示产品、数据、接口、交互、安全和工程边界已经具体到可以拆成开发任务，并且关键验收条件能够追溯到设计来源。

不能仅凭“已有很多文档”宣布完成。所有必需交付物必须存在、相互一致，并通过最后的逐项审计。

## 3. 允许留到实施阶段的内容

以下内容不阻塞设计阶段收尾，但必须有明确验证入口：

- RuoYi 上游代码的实际导入和编译结果；
- JDK 21、MySQL 8.4、Redis 7.x 的本地兼容性实测；
- 统一 npm lockfile 中的间接依赖版本；
- 百炼账号实际区域和模型权限；
- 浏览器执行引擎的真实性能数据；
- 最终视觉稿、品牌素材和逐像素样式；
- 真实用户可用性测试结果。

这些属于技术基线验证或实现验证，不得在设计阶段文档中伪装成已经通过。

## 4. 不允许遗留的模糊项

- “用户”到底指学生还是内部人员；
- 同一任务内容更新是否影响进行中体验；
- 推荐、AI 解释和学生改选谁是事实来源；
- 分析事件能否直接成为报告证据；
- 学生令牌是否可能访问管理接口；
- 任务进度和报告是否只存在 Redis；
- 报告生成失败是否意味着任务未完成；
- 删除账户后哪些可识别数据仍然存在；
- 重复提交、自动保存乱序和重复开始任务如何处理；
- 管理人员是否可以修改学生答案或伪造完成状态；
- 任何 API Key 是否可能进入前端、日志或仓库。
- 活动与暂停体验如何切换，异常恢复如何释放唯一约束而不伪造完成；
- Cookie Path 是否实际覆盖注册认领、退出和删除状态查询；
- 推荐平局能否输入、每个排序键是否有效、理由是否真实；
- 快照重试版本、关闭时机、持久化作业和删除竞态是否一致；
- 浏览器练习与服务端隐藏评价的资产和可信结果是否分离。

## 5. 最终审计方法

设计交付物完成后执行以下审计：

1. 从 `01` 的每个必须功能和验收条目反向找到对应专题设计；
2. 从每个 API 和数据表正向找到产品需求或运行约束；
3. 用正常、重复提交、失败恢复、越权、任务升级、报告失败、删除账户七类场景走查；
4. 检查学生端、管理端、后端、MySQL、Redis、浏览器执行和模型服务的责任是否唯一；
5. 检查所有“待确认”“建议”“以后决定”是否已处理，或明确属于允许留到实施阶段的验证项；
6. 检查文档链接、术语和状态是否一致；
7. 输出设计阶段完成审计，逐项给出已证明、未证明或不适用的证据。

只有 D1–D15 全部满足，才能将设计阶段标记为完成。
